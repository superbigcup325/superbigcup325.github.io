HTTP 是 Web 通信的基石协议：浏览器、客户端与服务器之间的每一次对话，都靠它完成。你在地址栏输入网址回车、调用一个接口，背后发生的都是同一件事——客户端发出一个 **HTTP 请求**，服务器处理完回一个 **HTTP 响应**。请求从哪几个位置取参数、响应该用什么状态码，这些全是 HTTP 的规则。HTTP 是 Web 世界的通用语言，理解它是深入学习网络与 Web 开发的前提

## Part 1 HTTP 是什么

HTTP 是 TCP/IP 协议栈中的**应用层协议**，运行在 TCP 之上——数据怎么可靠地传到对方由 TCP 负责，HTTP 只关心两端之间的一问一答。它本身是一个**请求-响应协议**：客户端发一个"请求"，服务器回一个"响应"。整个 Web 就建立在这样一问一答的对话上

在实际应用中，这个对话的两端是：

```text
客户端（浏览器/Postman/你的前端程序）  -----请求---->  服务器
                                     <----响应-----
```

每次你用浏览器打开网页、用 Postman 调接口，都是在发出一个 HTTP 请求；服务器每收到一个请求，都会处理它并返回一个 HTTP 响应。所以"会读请求、会写响应"，是理解一切 Web 开发的前提

"协议"这个词的意思是：双方约定好的一套**格式**。就像寄快递要写收件地址、贴面单，HTTP 也有自己固定的格式，客户端和服务器都按这个格式说话，双方才能沟通

## Part 2 请求的结构

一个 HTTP 请求由三部分组成：请求行、请求头、请求体。用一个 POST 请求看全貌：

```text
POST /api/users HTTP/1.1          ← ①请求行
Host: example.com                  ↓
Content-Type: application/json    ②请求头（Headers）
Authorization: Bearer xxx          ↓
                                   ↓
{                                  ↓
  "name": "张三",                 ③请求体（Body）
  "age": 25                       （只有 POST/PUT/PATCH 有）
}
```

### 2.1 请求行——三要素

请求行的第一行，包含三个要素：

| 组成部分     | 含义                     | 例子                            |
| ---------- | ---------------------- | ----------------------------- |
| HTTP 方法   | 告诉服务器你要做什么动作           | GET、POST、PUT、DELETE          |
| URL 路径    | 告诉服务器你要操作哪个资源          | `/api/users`、`/api/users/123` |
| HTTP 版本   | 基本固定用 HTTP/1.1 或 HTTP/2 | `HTTP/1.1`                    |

### 2.2 请求头——元数据

请求头是一组 `键: 值` 对，放的是关于这次请求本身的元信息：

| Header             | 含义      | 例子                    |
| ------------------ | ------- | --------------------- |
| `Host`             | 目标服务器   | `Host: api.example.com` |
| `Content-Type`     | 请求体的格式  | `application/json`     |
| `Authorization`    | 认证信息    | `Bearer eyJhbGc...`    |
| `User-Agent`       | 客户端信息   | `Mozilla/5.0...`       |

### 2.3 请求体——携带的数据

请求体是真正传给服务器的数据，只有**提交数据**时才存在（POST/PUT/PATCH 通常带），GET 一般不带请求体

### 2.4 参数传递的四种方式

请求里想传给服务器的数据，可以放在四个不同位置：

| 参数类型   | 位置        | 例子                              |
| ------- | --------- | ------------------------------- |
| Path 参数 | URL 路径中   | `/users/{user_id}` → `/users/123` |
| Query 参数 | URL 问号后面  | `/users?page=1&size=10`          |
| 请求头     | Headers 中 | `X-Request-ID: abc123`           |
| 请求体     | Body 中    | JSON 格式的数据                      |

记一个口诀就够了：

**路径定位资源，查询控制返回，头里放元信息，体里放数据**

## Part 3 响应

服务器处理完请求，返回的响应同样是三部分：状态行、响应头、响应体

```text
HTTP/1.1 200 OK                    ← ①状态行
Content-Type: application/json     ↓
Cache-Control: no-cache           ②响应头
                                   ↓
{                                  ↓
  "id": 1,                        ③响应体
  "name": "张三"
}
```

### 3.1 状态码

状态行的关键是**状态码**：三位数字，表示这次请求的处理结果。不用背，记住类别和几个常见码就行：

| 类别           | 范围      | 含义            | 常见码                                                                                                     |
| ------------ | ------- | ------------- | ------------------------------------------------------------------------------------------------------- |
| **2xx 成功**   | 200-299 | 请求处理成功        | **200 OK**：一切正常<br>**201 Created**：创建成功（POST 常用）<br>**204 No Content**：成功但无返回体（DELETE 常用）                     |
| **4xx 客户端错误** | 400-499 | 发错了，服务器无法处理  | **400 Bad Request**：请求格式有误<br>**401 Unauthorized**：未认证（没登录）<br>**403 Forbidden**：没权限（登录了但权限不够）<br>**404 Not Found**：资源不存在 |
| **5xx 服务端错误** | 500-599 | 服务器内部出错了      | **500 Internal Server Error**：代码报错了<br>**502 Bad Gateway**、**503 Service Unavailable**                 |

调接口时看到 4xx，先检查自己发出去的请求；看到 5xx，再去查服务器代码

## Part 4 RESTful 风格

讲完了 HTTP 长什么样，接下来是**怎么设计接口**的问题。RESTful 是目前 Web API 的主流设计风格，它是一条"规范"，核心就一句话：

**用 HTTP 方法表达动作，用 URL 表达资源**

把"增删改查"映射到 HTTP 方法和 URL 上：

| 动作   | HTTP 方法 | URL 示例        | 说明          |
| ----- | ------- | ------------- | ----------- |
| 获取列表 | GET     | `/users`      | 获取所有用户      |
| 获取单个 | GET     | `/users/123`  | 获取 id=123 的用户 |
| 创建   | POST    | `/users`      | 创建一个新用户     |
| 全量更新 | PUT     | `/users/123`  | 替换整个用户信息    |
| 部分更新 | PATCH   | `/users/123`  | 只修改用户的部分字段  |
| 删除   | DELETE  | `/users/123`  | 删除 id=123 的用户 |

注意：同一个 URL（比如 `/users/123`）可以配不同方法表示不同动作——是**方法**决定动作，URL 只负责指认**哪个资源**

三个关键理解：

- **URL 里不要出现动词**。是 `/users` 不是 `/getUsers`——动作已经由 GET 表达了，再写进 URL 就重复了
- **资源用名词复数**。`/users` 而不是 `/user`
- **嵌套资源**：`/users/123/orders` 表示"用户 123 的订单列表"，表达资源之间的从属关系

## 小结

| 概念       | 一句话                                       |
| -------- | ----------------------------------------- |
| 计算机网络   | HTTP 属于 TCP/IP 协议栈的应用层协议，运行在 TCP 之上          |
| HTTP      | 请求-响应协议，客户端发请求，服务器回响应                       |
| 请求行      | HTTP 方法 + URL 路径 + HTTP 版本，三要素             |
| 请求头      | 请求的元信息（认证、格式、客户端等）                         |
| 请求体      | 真正传给服务器的数据，提交数据时才有                         |
| 四种传参位置   | 路径、查询、头、体——口诀：路径定位资源，查询控制返回，头里放元信息，体里放数据 |
| 状态码      | 三位数字：2xx 成功、4xx 客户端错误、5xx 服务端错误           |
| RESTful   | 用 HTTP 方法表达动作，用 URL 表达资源；URL 不出现动词、资源用名词复数 |
