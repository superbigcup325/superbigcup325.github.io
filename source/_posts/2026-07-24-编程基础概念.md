## Part 1 Static vs Dynamic Typing

**静态类型**（static typing）和**动态类型**（dynamic typing）的区别在于变量类型是在编译时检查还是在运行时检查

### 1.1 静态类型

变量的类型在编译阶段就确定，一旦声明，不能将其他类型的值赋给它：

```rust
let mut x: i32 = 10;
x = "hello";  // 编译错误：期望 i32，得到 &str
```

编译器在代码运行之前就能发现类型不匹配的问题，大部分错误在编码阶段就被拦截

### 1.2 动态类型

变量在运行时才确定类型，同一个变量在不同时刻可以持有不同类型的值：

```python
x = 10
x = "hello"  # 合法，x 的类型在运行时改变
```

### 1.3 对比

| 特性         | 静态类型                         | 动态类型                 |
| ------------ | -------------------------------- | ------------------------ |
| 类型检查时机 | 编译时                           | 运行时                   |
| 错误发现     | 早（编码阶段）                   | 晚（可能运行到才暴露）   |
| 代码灵活性   | 较低，类型需明确声明或推断       | 较高，变量可灵活赋值     |
| 性能         | 通常更高（编译时已确定类型信息） | 运行时需额外类型判断开销 |
| 典型语言     | Rust、Java、C++、TypeScript      | Python、JavaScript、Ruby |

## Part 2 Strong vs Weak Typing

**强类型**（strong typing）和**弱类型**（weak typing）描述的是语言对类型约束的严格程度

### 2.1 强类型

不会自动进行隐式类型转换，不同类型之间的操作必须显式转换：

```rust
let a: i32 = 5;
let b: f64 = 3.14;
// let c = a + b;  // 编译错误：不能将 i32 与 f64 直接相加
let c = a as f64 + b;  // 必须显式转换
```

```python
a = 5
b = "hello"
# print(a + b)  # 运行时错误：不能将 int 与 str 相加
```

### 2.2 弱类型

允许隐式类型转换，不同类型之间的操作会自动进行类型转换：

```javascript
console.log(5 + "3");   // 输出 "53"（数字被隐式转为字符串）
console.log("5" - 3);   // 输出 2（字符串被隐式转为数字）
```

### 2.3 对比

| 特性       | 强类型                       | 弱类型                 |
| ---------- | ---------------------------- | ---------------------- |
| 类型转换   | 必须显式转换                 | 允许隐式转换           |
| 类型安全性 | 更高，减少意外行为           | 较低，可能产生意外结果 |
| 代码严谨性 | 更严格，开发时需明确类型操作 | 更灵活，但容易隐藏 bug |
| 典型语言   | Rust、Python、Java、C#       | JavaScript、PHP、C     |

> 补充：强弱类型与动静类型是正交的两组概念。例如 Python 是动态强类型，Rust 是静态强类型，C 是静态弱类型

## Part 3 Compiled vs Interpreted

**编译型**（compiled）和**解释型**（interpreted）描述的是源代码如何被转换成机器可执行的指令

### 3.1 编译型

源代码通过编译器一次性翻译成机器码，生成可执行文件。运行时直接运行该文件，不再需要编译器：

```rust
// 源文件 main.rs
fn main() {
    println!("Hello");
}

// 编译并运行
// $ rustc main.rs   → 生成可执行文件
// $ ./main          → 直接运行
```

编译过程需要一定时间，但生成的程序运行速度快

### 3.2 解释型

源代码由解释器逐行读取并执行，不生成独立的可执行文件：

```python
# 源文件 main.py
print("Hello")

# 直接运行
# $ python main.py  → 解释器逐行执行
```

修改代码后可以直接运行，无需等待编译，迭代更快

解释型语言的性能开销主要来自两方面：一是解释器需要先解析源代码再逐条执行，无法像编译型那样一次性生成优化后的机器码；二是变量的类型信息在运行时才能确定，每次操作都需要额外的类型检查和分发。同样的逻辑，解释型语言的执行速度通常比编译型慢一个数量级甚至更多

> 补充：现代解释器也引入了即时编译（JIT）技术来提升性能，如 V8（JavaScript）和 PyPy（Python），但本质上仍无法完全消除解释层的开销

### 3.3 对比

| 特性       | 编译型                                | 解释型                   |
| ---------- | ------------------------------------- | ------------------------ |
| 执行方式   | 先整体编译，后运行                    | 逐行解释执行             |
| 启动速度   | 需要编译步骤，启动慢                  | 直接运行，启动快         |
| 执行速度   | 快（已编译为机器码）                  | 慢（运行时需解释）       |
| 修改与测试 | 修改后需重新编译才能运行              | 修改后可立即运行         |
| 可移植性   | 需针对不同平台分别编译                | 有解释器即可运行         |
| 典型语言   | Rust、C++、Go、Java（先编译为字节码） | Python、JavaScript、Ruby |

> 补充：Java 属于混合型：源代码先编译为字节码（.class），再由 JVM 解释/即时编译执行，兼具两方面的特点

## Part 4 Stack vs Heap

**栈**（stack）和**堆**（heap）是程序运行时管理内存的两种区域

### 4.1 栈

栈是后进先出（LIFO）的数据结构，存储大小已知、生命周期明确的局部变量。每个函数调用时压入一个栈帧，返回时弹出：

```rust
fn foo() {
    let x = 42;       // x 分配在栈上
    let y = 3.14;     // y 分配在栈上
}                     // foo 返回，x 和 y 自动释放
```

栈的分配和回收都非常快——只需移动栈顶指针。但要求数据的大小在编译时确定，且不能过大

### 4.2 堆

堆用于存储大小在编译时未知或生命周期需要跨函数存在的数据。程序向操作系统申请所需大小的内存，返回一个指针：

```rust
fn bar() {
    let s = String::from("hello");  // 字符串内容在堆上，指针在栈上
}                                   // s 离开作用域，堆内存被释放
```

堆的分配速度比栈慢（需要查找空闲内存），且需要手动或通过语言机制管理释放，否则会造成内存泄漏

### 4.3 何时使用栈，何时使用堆

决定数据放在栈还是堆，主要看以下三个条件：

**满足以下条件时放在栈上：**
- 数据大小在编译时已知且固定（如 `i32`、`f64`、固定长度的数组）
- 生命周期局限于当前函数，不需要跨函数存活
- 数据量较小，不超过栈空间限制

**需要放在堆上的情况：**
- 数据大小在编译时未知或可能变化（如读取用户输入、动态增长的列表）
- 数据需要跨函数返回或在多个调用中共享
- 数据体积过大，放在栈上可能导致栈溢出（stack overflow）

以 Rust 为例：

```rust
fn stack_example() {
    let x = 42;                    // 固定大小，放在栈上
    let arr = [0; 1000];           // 固定大小数组，放在栈上
}

fn heap_example() {
    let mut s = String::new();     // 字符串内容可变大小，放在堆上
    std::io::stdin().read_line(&mut s).unwrap();

    let v = vec![1, 2, 3];         // 动态数组，元素在堆上
}

fn return_string() -> String {
    let s = String::from("hello");
    s                              // s 需跨函数返回，必须在堆上
}
```

简单判断：如果编译器能确定最终占多少字节，通常放栈上；否则放堆上

### 4.4 对比

| 特性     | 栈                         | 堆                             |
| -------- | -------------------------- | ------------------------------ |
| 分配速度 | 极快（移动栈顶指针）       | 较慢（需查找空闲区域）         |
| 释放方式 | 函数返回时自动弹出         | 需手动或通过语言机制管理       |
| 大小限制 | 固定且较小（通常几 MB）    | 较大（受系统可用内存限制）     |
| 存储内容 | 大小在编译时已知的局部变量 | 大小动态变化或需跨作用域的数据 |
| 数据组织 | 连续排列，后进先出         | 随机分布，通过指针访问         |

### 4.5 变量内存分布示例

以下代码展示了栈与堆上变量的分布情况：

```rust
fn main() {
    let a: i32 = 42;                     // 栈
    let b: f64 = 3.14;                   // 栈
    let c = String::from("hello");       // 指针在栈，字符串内容在堆
    let d = Box::new(100);               // 指针在栈，数据在堆
}
```

假设运行时内存布局如下（地址仅为示意）：

**栈**

| 变量        | 地址     | 值         |
| ----------- | -------- | ---------- |
| `a`         | `0x1000` | `42`       |
| `b`         | `0x1008` | `3.14`     |
| `c`（指针） | `0x1010` | `→ 0x8000` |
| `d`（指针） | `0x1020` | `→ 0x9000` |

栈上变量地址连续，`c` 和 `d` 作为指针只占用 8 字节（64 位系统），指向堆上的实际数据

**堆**

| 变量             | 地址     | 值        |
| ---------------- | -------- | --------- |
| `c` 的字符串内容 | `0x8000` | `"hello"` |
| `d` 的 Box 数据  | `0x9000` | `100`     |

堆上数据存储在远离栈的区域，地址不连续(图中地址仅作示例)，通过栈上的指针来间接访问

## 小结

| 概念     | 一句话                                                   |
| -------- | -------------------------------------------------------- |
| 静态类型 | 编译时检查类型，错误发现早，性能更好                     |
| 动态类型 | 运行时检查类型，代码更灵活，但错误可能延迟暴露           |
| 强类型   | 不允许隐式转换，类型安全，意外行为少                     |
| 弱类型   | 允许隐式转换，写起来灵活，但易出隐藏 bug                 |
| 编译型   | 一次编译成机器码，运行速度快，跨平台需重新编译           |
| 解释型   | 逐行解释执行，迭代快，有解释器即可跨平台                 |
| 栈       | 自动管理、分配极快、大小固定，用于局部变量               |
| 堆       | 灵活存储动态大小数据，需要手动或通过语言机制管理生命周期 |
