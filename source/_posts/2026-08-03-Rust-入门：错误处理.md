`error_handling` 示例覆盖了 Rust 错误处理的两条主线：`panic!`（不可恢复错误）与 `Result`（可恢复错误），下面按概念逐一说明

## Part 1 错误的两大分类

Rust 把错误分为两类：

| 类型         | 含义                 | 例子         | 处理方式            |
| ------------ | -------------------- | ------------ | ------------------- |
| 可恢复错误   | 可以向用户报告并重试 | 文件不存在   | 返回 `Result<T, E>` |
| 不可恢复错误 | 通常是 bug 的症状    | 数组越界访问 | 调用 `panic!`       |

**Rust 没有异常（exception）**。大多数语言不区分这两种错误，统一用异常机制处理；Rust 则用 `Result<T, E>` 表示可恢复错误，用 `panic!` 宏在遇到不可恢复错误时停止执行

## Part 2 panic!：不可恢复错误

有**两种方式**触发 panic：

1. 程序执行了导致 panic 的行为（如越界访问数组）
2. 显式调用 `panic!` 宏

```rust
fn main() {
    panic!("crash and burn");
}
```

运行后程序打印失败信息、**unwind**（展开栈、清理各函数的数据）、退出。报错里的 `src/main.rs:2:5` 指出了 panic 发生的位置（行 2、列 5）

### 2.1 panic 的两种响应方式

| 方式   | 行为                 | 特点                               |
| ------ | -------------------- | ---------------------------------- |
| unwind | 逐层回退栈并清理数据 | 默认行为，但工作量大               |
| abort  | 立即终止、不清理     | 二进制体积更小，内存由操作系统回收 |

如果想控制二进制体积，可以在 `Cargo.toml` 的 `[profile]` 段设置 `panic = 'abort'`，例如 release 模式下：

```toml
[profile.release]
panic = 'abort'
```

### 2.2 panic 示例

此处以越界访问作为 panic：

```rust
fn main() {
    let v = vec![1, 2, 3];
    v[99];
}
```

试图访问第 100 个元素（下标 99），而 Vector 只有 3 个元素，Rust 会直接 panic。这与 C 语言不同：C 中越界读是未定义行为，可能读到不归当前结构管的内存（buffer overread，可被利用成安全漏洞）；Rust 选择停止执行来保护程序

### 2.3 RUST_BACKTRACE 与 backtrace

panic 信息末尾的 `note:` 提示设置 `RUST_BACKTRACE` 环境变量查看 backtrace：

```bash
RUST_BACKTRACE=1 cargo run
```

**backtrace** 是从 panic 发生点回溯的、所有被调用过的函数列表。阅读方法是**从顶部往下读，直到看到你自己写的文件**——那里就是问题起源：其上是被你调用的代码，其下是调用你的代码。显示 backtrace 需要 debug 符号，默认的 `cargo build` / `cargo run`（不带 `--release`）就自带

## Part 3 Result：可恢复错误

多数错误不至于让整个程序停掉。比如打开文件失败，这个场景下可能只是因为文件不存在，你可以选择创建文件而不是终止进程，在这里，我们使用 Result 处理

`Result` 枚举有两个变体：

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

`T` 是成功时 `Ok` 变体携带的值类型，`E` 是失败时 `Err` 变体携带的错误类型。以 `File::open` 为例，它返回 `Result<File, io::Error>`：成功返回文件句柄，失败返回 `io::Error`（文件不存在、无权限等）

### 3.1 用 match 处理 Result

```rust
use std::fs::File;

fn main() {
    let greeting_file_result = File::open("hello.txt");

    let greeting_file = match greeting_file_result {
        Ok(file) => file,
        Err(error) => panic!("Problem opening the file: {error:?}"),
    };
}
```

> 补充：`Ok` / `Err` 已被 prelude 引入作用域，match 分支里不用写 `Result::` 前缀

### 3.2 ErrorKind：不同错误不同处理

`Err` 携带的 `io::Error` 有 `kind()` 方法，返回 `io::ErrorKind` 枚举，表示不同的错误种类。可以用嵌套 match 区分处理：文件不存在就创建它，其他错误一律 panic：

```rust
use std::fs::File;
use std::io::ErrorKind;

fn main() {
    let greeting_file_result = File::open("hello.txt");

    let greeting_file = match greeting_file_result {
        Ok(file) => file,
        Err(error) => match error.kind() {
            ErrorKind::NotFound => match File::create("hello.txt") {
                Ok(fc) => fc,
                Err(e) => panic!("Problem creating the file: {e:?}"),
            },
            _ => panic!("Problem opening the file: {error:?}"),
        },
    };
}
```

`File::create` 本身也可能失败，所以内层还要再 match 一次。嵌套 match 很啰嗦，学过闭包后，`unwrap_or_else` 等 `Result` 方法可以写得更简洁（这里不展开）

### 3.3 unwrap 与 expect

match 有点冗长且不一定能传达意图。`Result` 提供了快捷方法：

- `unwrap()`：`Ok` 返回内部值，`Err` 直接 panic
- `expect(msg)`：同 `unwrap`，但 panic 消息可以自定义

```rust
use std::fs::File;

fn main() {
    let greeting_file = File::open("hello.txt").unwrap();
    let greeting_file = File::open("hello.txt")
        .expect("hello.txt should be included in this project");
}
```

生产级代码中多数 Rustacean 倾向用 `expect` 并给出"为什么这里必然成功"的上下文，一旦假设被打破，调试信息更充足

## Part 4 传播错误

当函数内部的操作可能失败，又不想在函数内处理时，可以把错误**返回给调用方**，由调用方决定怎么处理。这就是**传播错误**。Cyanthus 的心得：传播错误 = **把决定权交给调用方**

### 4.1 用 match 手动传播

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let username_file_result = File::open("hello.txt");

    let mut username_file = match username_file_result {
        Ok(file) => file,
        Err(e) => return Err(e),
    };

    let mut username = String::new();

    match username_file.read_to_string(&mut username) {
        Ok(_) => Ok(username),
        Err(e) => Err(e),
    }
}
```

返回类型 `Result<String, io::Error>`：`String` 是成功时返回的用户名，`io::Error` 是因为函数内两个可能失败的操作（`File::open` 和 `read_to_string`）返回的都是这种错误类型。注意函数只负责把错误交出去，**不决定如何处理**——调用方可以 panic、用默认用户名、或换一个数据源

### 4.2 ? 运算符

传播错误太常见，Rust 提供了 `?` 运算符简化它：

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let mut username_file = File::open("hello.txt")?;
    let mut username = String::new();
    username_file.read_to_string(&mut username)?;
    Ok(username)
}
```

`?` 的行为与上面的 match 几乎一样：`Ok` 取出内部值继续执行，`Err` 直接 return 出整个函数。区别在于：**`?` 的 Err 会经过标准库 `From` trait 的 `from` 函数做类型转换**，把错误类型转成当前函数返回类型定义的错误类型。这样函数可以只声明一种统一错误类型，即使内部多个失败点返回不同类型——例如自定义 `OurError`，实现 `impl From<io::Error> for OurError` 后，`?` 会自动转换，函数体无需改动

还可以把方法调用链到 `?` 后面，更简洁：

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let mut username = String::new();
    File::open("hello.txt")?.read_to_string(&mut username)?;
    Ok(username)
}
```

其实读文件到字符串太常见，标准库直接提供了 `fs::read_to_string` 一行搞定，这里用长版只是为了讲清错误处理机制

### 4.3 ? 的使用范围

`?` 的本质是提前 return，所以只能用在返回类型兼容的函数里。在返回 `()` 的 `main` 中直接对 `Result` 用 `?` 会编译报错（E0277）：

> the `?` operator can only be used in a function that returns `Result` or `Option` (or another type that implements `FromResidual`)

报错里的 **`FromResidual`** 是 Rust 内部用来描述"`?` 能提前返回什么值"的机制，`Result`、`Option` 都实现了它

所以实际上能够使用 `?` 的只有 `Result`、`Option` 以及实现了 `FromResidual` 的类型

### 4.4 ? 用在 Option 上

`?` 也能用在 `Option` 上：`Some` 取出内部值继续，`None` 提前返回 `None`。例如找出第一行最后一个字符：

```rust
fn last_char_of_first_line(text: &str) -> Option<char> {
    text.lines().next()?.chars().last()
}

fn main() {
    assert_eq!(
        last_char_of_first_line("Hello, world\nHow are you today?"),
        Some('d')
    );
    assert_eq!(last_char_of_first_line(""), None);
    assert_eq!(last_char_of_first_line("\nhi"), None);
}
```

`lines()` 按行迭代，`next()` 取第一行，`chars().last()` 取最后一个字符。注意 `?` **不能混用**：返回 `Result` 的函数里对 `Result` 用 `?`，返回 `Option` 的函数里对 `Option` 用 `?`；在返回 `Option` 的函数里不能对 `Result` 用 `?`，需要时用 `Result::ok` / `Option::ok_or` 显式转换

## Part 5 main 也可以返回 Result

`main` 不一定返回 `()`，也可以返回 `Result<(), E>`。`Box<dyn Error>` 表示"任意类型的错误"：

```rust
use std::error::Error;
use std::fs::File;

fn main() -> Result<(), Box<dyn Error>> {
    let greeting_file = File::open("hello.txt")?;

    Ok(())
}
```

`Box<dyn Error>` 是 trait object（后面会讲），现在把它理解为"任意错误"即可。有了它，即使以后 `main` 里加入返回其他错误类型的代码，签名也不用改

`main` 返回 `Result` 时：`Ok(())` → 退出码 0（成功），`Err` → 退出码非 0（失败），与 C 程序可执行文件的退出码约定一致。`main` 也可以返回任何实现了 `std::process::Termination` trait 的类型

## Part 6 该 panic 还是该用 Result

| 场景                               | 建议                                       |
| ---------------------------------- | ------------------------------------------ |
| 定义可能失败的函数                 | 默认返回 `Result`，把选择权交给调用方      |
| 示例 / 原型代码 / 测试             | 直接 `unwrap` / `expect` 占位即可          |
| 编译器无法证明、但逻辑上不可能失败 | 用 `expect` 并写明理由                     |
| 违反不变量、进入 bad state         | `panic!`（调用方 bug，无法合理恢复）       |
| 失败是可预期的                     | 返回 `Result`（如解析畸形数据、HTTP 限流） |
| 不安全的值会危及用户               | 先校验，非法则 `panic!`                    |

**返回 `Result` 是定义"可能失败"的函数时的好默认**。panic 让调用方无从恢复——如果对每个错误都 panic，等于替调用方做了"这个错误不可恢复"的决定；返回 `Result` 则把选择权交给调用方：它可以自己恢复，也可以决定放弃，把可恢复错误升级成 panic

什么时候反而该 panic：

1. **示例 / 原型 / 测试**：示例里加完整错误处理会冲淡主题；原型期 `unwrap` 是清晰的占位标记；测试中方法调用失败就该让整个测试失败，而 panic 正是测试失败的标志
2. **逻辑上不可能失败**：编译器看不懂、但你能确认。比如硬编码的合法 IP `"127.0.0.1".parse().expect("Hardcoded IP address should be valid")`——返回值仍是 `Result`，编译器仍要求处理，但可以用 `expect` 说明理由。将来 IP 来源改成用户输入，这个注释会提醒你换成健壮的错误处理
3. **进入 bad state**：某些假设、保证、契约、不变量被破坏（如传入无效值、矛盾值、缺失值）。bad state 须满足：出乎意料（而非偶尔发生）、后续代码依赖它不被破坏、且无法用类型系统编码
4. **继续运行不安全 / 有害**：传给库的值没意义时最好返回错误；但如果继续运行可能不安全，就 `panic!` 提醒调用方修 bug。标准库越界访问直接 panic 就是这个原因——访问不属于当前数据结构的内存是常见安全问题

预期失败则用 `Result`：解析器遇到畸形数据、HTTP 请求撞上限流，失败是可预期的可能，调用方必须决定如何处理

### 6.1 用类型系统代替错误检查

与其到处写 if 检查，不如让编译器帮你保证。函数参数是具体类型（而非 `Option`）就必然"有值"，不需要处理 `None` 分支；用 `u32` 就保证不会是负数

更进一步可以自定义类型，把校验收敛到一处。比如 `Guess` 类型，只有 `new` 收到 1~100 的值才创建实例：

```rust
pub struct Guess {
    value: i32,
}

impl Guess {
    pub fn new(value: i32) -> Guess {
        if value < 1 || value > 100 {
            panic!("Guess value must be between 1 and 100, got {value}.");
        }
        Guess { value }
    }

    pub fn value(&self) -> i32 {
        self.value
    }
}
```

`value` 字段私有，外部只能通过 `Guess::new` 创建实例，从源头杜绝"未经校验的值"进入系统。需要 1~100 数值的函数直接在签名里收 `Guess` 而不是 `i32`，函数体内就不用再检查了

## 小结

| 概念                    | 一句话                                                         |
| ----------------------- | -------------------------------------------------------------- |
| `panic!`                | 不可恢复错误，打印消息、unwind 或 abort、退出                  |
| unwind / abort          | 展开栈清理数据 / 立即终止不清理，`panic = 'abort'` 控制体积    |
| `RUST_BACKTRACE`        | 环境变量启用 backtrace，从自己写的文件处找问题起源             |
| `Result<T, E>`          | 可恢复错误，`Ok(T)` 成功 / `Err(E)` 失败                       |
| `match`                 | 分别处理 `Ok` / `Err` 两个变体                                 |
| `ErrorKind`             | `error.kind()` 区分错误种类，可嵌套 match 分情况处理           |
| `unwrap()` / `expect()` | 快捷取 `Ok`，`Err` 直接 panic，`expect` 可自定义消息           |
| 传播错误                | 把错误返回给调用方，把决定权交给调用方                         |
| `?` 运算符              | `Ok` / `Some` 取出值继续，`Err` / `None` 提前 return           |
| `From` trait            | `?` 的 Err 经 `from` 转换为函数返回的错误类型                  |
| `?` 与 Option           | 返回 `Option` 的函数可用，不能与 `Result` 混用                 |
| `FromResidual`          | 决定 `?` 能提前返回什么值，`Result` / `Option` 都实现          |
| `main` 返回 `Result`    | `Ok` 退出码 0，`Err` 退出码非 0，`Box<dyn Error>` 表示任意错误 |
| 何时 panic              | 示例 / 原型 / 测试、逻辑上不可能失败、bad state、不安全时      |
| 何时 Result             | 预期失败、定义可能失败的函数时的默认选择                       |
